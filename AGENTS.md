# Sumi Language Core

You're in the core repository for Sumi, a novel statically typed general-purpose programming language.

## Git Style

- Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) with the following types: build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test.
- Commits should be self-contained, directed, and easily reviewable.

## Crates

- Dependencies point one way. Each line names what a crate owns and what it sits on directly; what those sit on follows.
- `sumi-text`: offsets, ranges, edits, and the line index. Depends on nothing.
- `sumi-lexer`: the total, lossless lexer and the token vocabulary. On `sumi-text`.
- `sumi-syntax`: the parser, the flat tree and its reprint, parse evidence, recovery, and the node vocabulary with its typed views. On `sumi-lexer`.
- `sumi-format`: `format` and its contract `rep`. On `sumi-syntax`.
- `sumi-frontend`: the diagnostic type every later phase reports with, and `parse_source`, which owns the source and lowers the lexer's and parser's evidence into diagnostics. On `sumi-syntax`.
- `sumi-graph`: what a program means apart from whether it is valid: the types, `Int`, the `Graph`, the may-domain, and the concrete `Machine`. Depends on nothing, and nothing here depends on the checker; where a node comes from in the source is `sumi-hir`'s `Spans`.
- `sumi-opt`: the middle end: `optimize` rewrites a proven graph into a smaller, equally well-formed one that computes the same values, and maps each node to the one it came from, whose facts a backend reads. On `sumi-graph` only; it reads no diagnostic.
- `sumi-hir`: semantic checking: `analyze` builds the graph and decides what is wrong with it, and `Program`, the proof that a file is valid, compiles it through `sumi-opt` and runs it. On `sumi-frontend`, `sumi-graph`, and `sumi-opt`.
- `sumi-cli`: the `sumi` driver. On `sumi-frontend` and `sumi-hir` to check and run, and on `sumi-lexer`, `sumi-syntax`, and `sumi-format` to format, which reads no diagnostic.
- `sumi-test`: the program generator, edits, layout perturbation, the coverage account, the invariant checks the property tests and the fuzz targets share, and the fuzz seeder. On every crate but `sumi-graph` and `sumi-opt`, whose vocabulary it takes through `sumi-hir`; nothing ships it.
- `sumi-scorecard`: the recovery scorecard, a leaf on `sumi-test`; nothing ships it.
- `sumi-fuzz` (`fuzz/`): the fuzz targets, a leaf above every crate; nothing ships it.
- A crate's integration tests may use crates above it, which Cargo allows. A library's unit tests never import a crate above it: rust-analyzer's crate graph has no room for that cycle and drops the edge without a word, leaving those tests unresolved in the editor.

## Formatting

- `sumi fmt` is `sumi-format`'s `format`: one separator per gap between significant tokens, groups fitted to a width, and the parser's own newline rule deciding where a break is legal. Its contract is `rep`: the formatted text has the layout-free content of the source — the same tokens, tree, comments, and retained blank lines — or the disagreeing item is left as written, or the whole is a `Defect`. Gaps the parser recovered around are frozen. Add a layout rule per node kind in `plan.rs`; the corpus's `== formatted ==` sections and the `fmt` properties are the witnesses.

## Grammar and diagnostics

- The token vocabulary is one `tokens!` declaration in `crates/lexer/src/kind.rs`, which derives the keyword and punctuation tables, texts, and descriptions. The node vocabulary and the typed views are one `grammar!` declaration in `crates/syntax/src/ast.rs`: a struct per node kind listing the children the parser records, whose slots are their declaration order, then the `tokens` the rule holds itself, a named one read as a value; and an enum per category, with the name of its clean form. A kind's clean view, from `clean(tree, lexed)`, holds every required child and named token, so their accessors never answer `Option`. The token classes, bracket pairs, and operator tables are plain functions in `crates/syntax/src/grammar.rs`. Each member of an alternation a field admits that the corpus must reach is listed in `MEMBERS` in `crates/test/src/coverage.rs`: with the children and tokens the views declare, that is what the coverage check reads.
- A type list, `TypeParamList` or `TypeArgList`, runs from `<` to `>`, which are no bracket pair: `ParserInput` pairs the ones a name's glued `<` opens with no statement boundary inside, and in an expression only such a pair before a call's `(` is type arguments; any other `<` there is a comparison.
- A generic item is checked once, as its instance at its own type parameters, each a declared type with no fields that joins no union. Every other instance is a declared type or a function of its own, declared where it is first named and lowered in its turn, with its name and type diagnostics muted, so the graph, the solver, the machine, and `sumi-opt` see no type parameter. A symbol names the item, never an instance. A name with no type argument list takes the instance its use decides: a call's arguments against the parameters' types, a construction's field values against the fields', an arm the one member of the type matched; a type parameter nothing decides is `type-arguments`, and the list is written. An instance's body decides none: it takes what its item's own body decided, at its own type arguments.
- A body's types are checked as it is lowered: `typing.rs` walks each node once nothing built later changes what the walk reads of it, so lowering reads the type of what it has built through `Builder::ty`, and a decision that rests on a type is made there. A call reads the result its callee infers, so `Order` builds the function items callees first by the inferred results each body calls by name, and settles together a group that infers its results from one another; an instance takes its item's inferred result at its own type arguments. Node order is therefore build order, which `Graph::owner` reads back, and not item order.
- A place is a `mut` name and the fields under it. A write to one is its local's next version: each record on the way to the field made again, a `Make` over `Field` reads with the one field replaced, so the graph has no store and every write is exact. A compound assignment, `+=` and its kin, reads its place once, after its value, and its operator is two glued tokens like `==`. A `mut` parameter is its caller's place. Its function returns a product, a declared type of its own that holds the result and then each `mut` parameter's final value, which every exit makes; a call reads the result out of it and writes the rest back to the places, which are read where the call begins, after every argument. `Signature::returned` is the product, and `result` still the function's own.
- An `impl` names a type item and holds its methods: function items found by that type and their name, never by name alone, numbered where they stand among the items. Its type parameters are its own names for the type's, in scope before each method's own, and `Self` is the type at them. `self`, first among a method's parameters, is its receiver, of type `Self`. A method call, `MethodCallExpr`, is a call of the method its receiver's type gives the name, the receiver its first argument: the receiver decides the `impl`'s type parameters, and a type argument list is of the method's own. A receiver is written no `mut`: one its method takes as `mut self` is a place, read and written back as a `mut` argument is. A `.` glued to a name continues the line before, so a chain breaks before each `.`.
- `[T]` is a sequence of `T`: an instance of one built-in type item, after the source's, that has no fields and that `sumi-graph` knows by its element type, so type arguments, inference, and instance limits treat it as any generic type. A literal `[a, b]` takes its element type from what holds it to one, an annotation, a parameter, a field, a declared result, or a place assigned, and else from its first element with a type; `[]` has only the former. `xs[i]` is an element, its `[` on the line of what it indexes, and a step of a place beside a field: a write is `Store`, the sequence made again with one element replaced, and its index is read once, where the place is named. `len`, `push`, and `pop` are the compiler's methods of every sequence, `push` and `pop` of a `mut` place. A sequence's fact is the lengths it may have and what any element may hold, `Fields::Elements`; each element read or assigned needs its index inside the sequence, and each `pop` an element to take, `index-out-of-bounds`; a call's write back to a place it read is along the same lengths, and needs none. Two places are apart at indices written as different integers only.
- A call takes its callee's result at its own arguments. `summary.rs` passes each whole, well-typed body once, callees first, for its result as its parameters decide it: bounds over the parameters, their fields, and the lengths of their sequences, a few cases per integer, a `match` arm's only where its member reaches the scrutinee. A sequence stored into keeps the shape of the one it was, its length and its elements' at every depth. What a loop carries round is held to be what entered it, part by part, and the loop is passed again with what a pass did not keep until one keeps it all: an integer that changes is unknown, a sequence only stored into keeps its shape. The solver meets a call's result with the summary at the call's argument facts. A call inside a recursive group is unknown to the pass, so those results stay the hull over every caller.
- An operation that needs something of its operands to run, a divisor that is no zero, an index inside its sequence, an element to `pop`, is an `Obligation` lowering records, and `proof.rs` holds each to what is known in two steps. The values that may reach its operands decide most. What they leave open is read off the body: `summary.rs` passes it again with every node nothing decides named as a path of its own, so each integer is a linear form over parameters, lengths, elements, and such nodes, and a need is a `Claim` that a form is at least zero, or is not zero. The conditions on the way to the operation, the range of a loop's index, and what a call's summary bounds its result by are forms too, and a claim is proved by taking them from it until the values decide what is left. A function nothing calls is held to nothing.
- Diagnostic codes are one `codes!` declaration per group, in `crates/frontend/src/codes.rs` (`syntax`) and `crates/hir/src/codes.rs` (`semantic`), each code documented where it is declared with its severity, `Error` or `Warning`; an error rejects the program, a warning does not. The macro derives the constants and the group's `ALL`, so no code goes unlisted. To add a code, declare it there, emit it, and add a corpus case that shows it: `crates/hir/tests/codes.rs` fails on a code no snapshot reports at its severity. A code is never renamed or reused for something else, and never changes severity.

## Tests

- `tests/corpus/` at the workspace root is the shared file-based corpus. Every case directory holds `case.su` and `frontend.snap`, keeping the tree, parser evidence, frontend diagnostics, fixed source, and formatted source together; a case that selects `hir` leaves the tree out unless the parser recovered, since `hir.snap` anchors the graph the checker built by range, not every parse-tree node, so a case whose parse is the point does not select `hir`. `syntax/a-whole-program` is the tree golden of a large accepted file. `crates/frontend/tests/corpus.rs` runs every case through `sumi_test::corpus`, the runner every stage shares, which also lists the cases for any test that reads them; generate or update snapshots with `UPDATE_FRONTEND=1 cargo test -p sumi-frontend --test corpus`.
- For semantic-focused cases and useful recovery witnesses, not every syntax fixture, add a `stages` file listing `hir` to select an additional `hir.snap`, and `eval` (one name per line) to select an `eval.snap` that runs every parameterless function of an accepted case to its value, with the machine's step count and deepest call nesting beside the depth the analysis proved; a rejected case cannot select `eval`. Snapshot presence does not select a stage. Generate or update them with `UPDATE_HIR=1 cargo test -p sumi-hir --test corpus` and `UPDATE_EVAL=1 cargo test -p sumi-hir --test corpus`. Keep huge stress inputs out of golden snapshots. Review every generated diff.
- Behavior that a snapshot cannot express — invariants, API contracts, properties — stays in the crates' own tests. Every invariant is stated once, in `sumi-test`'s `check` module: a crate's property test samples it over generated sources, and the fuzz target of the same layer over arbitrary bytes, so a new invariant goes there and both find it. `crates/hir/tests/machine.rs` is the analysis held to the machine: generated programs the checker should accept, each run by `check::run` inside the parameter sets it proved and checked against its claims, on the analysis's graph and again optimized, where it must return the same value in no more steps; and doubtful ones, whose indices no guard quite covers, which must run as well wherever they are accepted. A change to what the checker accepts or proves, or to what `sumi-opt` rewrites, must keep that harness green.
- `crates/syntax/tests/coverage.rs` checks that the corpus and `sumi-test`'s program generator each reach every node kind and every child the grammar allows: the children and tokens every view declares, and `MEMBERS` in `crates/test/src/coverage.rs`. A grammar change therefore needs a corpus case and generator support before CI passes; the failure names what is missing.

## Fuzzing

- `fuzz/` is a libFuzzer package, `sumi-fuzz`, driven by [cargo-fuzz](https://rust-fuzz.github.io/book/cargo-fuzz.html): a leaf above every crate that nothing ships, like `sumi-scorecard`. Each target under `fuzz_targets/` feeds one layer's checks from `sumi-test` arbitrary input, the same checks that layer's property tests sample: `lex` the lexer, `parse` the whole frontend and formatter, `check` semantic acceptance and the graph's shape, `run` every accepted file on the machine inside the parameter sets the analysis proved, and `edit` single-edit recovery, with the fuzzer's bytes choosing the edit and the source in place of the generators of `sumi-test`. Proptest's pass-through RNG cannot stand in for the generators: it halves its bytes at every nested strategy, and the zeros it yields once they run out send rand's range sampling into an endless rejection loop.
- The crates are safe Rust, so run without a sanitizer, which is what keeps the stable toolchain enough: `cargo run -p sumi-test --bin fuzz-seed`, then `cargo fuzz run -s none parse -- -dict=fuzz/sumi.dict`. The seeds are the file-based cases; `edit` needs them, since mutation alone never assembles a program the parser accepts without evidence; `edit_seeds` in `sumi-test` writes them and `edit_input` beside it reads them, so the header is stated once. `fuzz/corpus/` and `fuzz/artifacts/` are untracked, and `fuzz/sumi.dict` lists every fixed token text; keep it with the `tokens!` declaration.
- A finding lands in `fuzz/artifacts/<target>/`. Minimize it with `cargo fuzz tmin -s none <target> <artifact>`, then keep it as a corpus case under `tests/corpus/` with the fix, so the regression stays found without the fuzzer. A nightly finding opens an issue, or comments on the open one with the same assertion shape, with the input shrunk and decoded by `fuzz-show` in `sumi-test`; `tmin` needs many attempts there, since most byte removals leave an input the target rejects.

## Code Style

- Follow YAGNI: don't implement functions which aren't necessary (also helps keep diffs reviewable)
- Prefer making invariants unrepresentable vs. adding asserts or explicit documentation.

## Comment Style

- A comment exists only to say what the code cannot: an invariant the types leave open, a contract the signature leaves open on an item others call, or why the obvious alternative is wrong, as a present-tense fact. Nothing else: not what the code does, not what a name already says, not what a test tests.
- One line, two at most; a module doc is at most two sentences. Plain register, noun first. Comments fill to 100 columns like the code.
- Private helpers, fields, variants, and tests carry no doc unless the name would mislead without one. A doc repeated on a caller and its callee stays on the callee. A `codes!` entry keeps one line: what triggers the code.
- No storytelling: how the code came to be, what it replaced, or what was tried belongs in the commit message, not the source.
- No speculative notes: no "could", "might", or "later"; work no one has committed to is not a comment.
- No references to external plans, designs, reviews, or conversations: a comment stands on the code alone, since that is all a reader has.
